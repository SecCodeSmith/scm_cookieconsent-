# Design

## Context

See proposal.md for the reason. Current state (1.8.0), with the code that matters:

- `views/js/src/gcm_bootstrap.src.js` is printed inline and first in `<head>` (`hookDisplayHeader`, `scm_cookieconsent.php:1053`). Its minified copy lives in `views/templates/hook/gcm_bootstrap.tpl` and must be regenerated by hand (`npx terser`). It reads the stored choice (cookie `scm_consent`, `localStorage` mirror), pushes the Consent Mode `default` (and an `update` for returning visitors), exposes `window.SCM_GCM` (`update`, `track`, `event`, `purchase`, `mode`, `ready`) and, at `DOMContentLoaded`, runs `injectGoogleTags()` (line 212), which loads GTM or `gtag.js` **regardless of consent**. `finish()` (line 191) flushes a pre-resolution queue. The Meta Pixel is already consent-gated (`applyMetaConsent`, line 105).
- The banner is `views/js/scm_cookieconsent.js` (+ `.min.js`), rendered by `views/templates/hook/cookie_banner.tpl` through whichever of three footer-ish hooks the theme calls (`renderBannerAndEcommerce()`, `scm_cookieconsent.php:1140`). On a user choice it calls `finalizeConsent()` (line 281): write cookie, `SCM_GCM.update(store)`, purge rejected cookies, hide banner.
- Events come from `views/js/scm_ecommerce.js` (`pushEvent`, `pushUserEvent`, `once()`; registered in `<head>`, runs at `DOMContentLoaded`) and from the inline `views/templates/hook/ecommerce_purchase.tpl`, whose `sessionStorage` guard is written when the event is queued.
- Facts checked against the 1.8.0 source while writing this change:
  - Optional categories do start off: every optional toggle is rendered `aria-checked="false"` in `cookie_banner.tpl` and `showBanner()` calls `setAllOptional(false)` when no complete stored choice exists. Closing the banner on a first visit rejects optional categories (`dismissBanner()`, line 295). No change needed here.
  - The default consent lifetime is 365 days (`EXPIRY_DAYS`, `scm_cookieconsent.php:451`) but the admin accepts 1 to 3650 (line 608).
  - No text footer link exists. `.scm-reopen-link` is only a click handler in `scm_cookieconsent.js` (line 460); the visible "Zmień ustawienia cookies" text is the `aria-label` and a screen-reader-only span of the round floating reopen button.
  - The first layer has three buttons; "Akceptuję wszystkie" is the filled primary-colour button with a shadow, "Zapisz" is outlined, "Odrzuć opcjonalne" is white with a grey border (`views/css/scm_cookieconsent.css:247-265`).
- Front-office JS stays ES5 with no dependencies (README promise). CI runs `php -l` and `build.ps1`; there are Playwright e2e tests in `tests/e2e/` (Docker PrestaShop 8.1, Edge) that block Google hosts at the network layer and read the dataLayer.
- The owner decided on 2026-11-15 for Consent Mode "basic" and accepts lower GA4 and Ads figures (modelling for refusers is lost).

## Goals / Non-Goals

**Goals:**
- Provable absence of requests to analytics and advertising hosts without a grant, with a request log in the tests.
- Delivery of the six e-commerce events after a late grant, unchanged in name and payload, in both tag modes.
- A small change: the bootstrap stays the single owner of loading and routing, as the in-flight changes designed it.

**Non-Goals:**
- Gating scripts that other modules print (an external GTM module). Out of reach of this module; documented instead.
- Replaying events across pages or storing events for later; a visitor who has not consented leaves no trace.
- Server-side tagging, enhanced conversions, a consent log on the server, a new banner design, a second language set of texts.
- Changing the GA4 event set (that is `complete-ga4-ecommerce-measurement`).

## Decisions

### D1. Tag loading moves from "every page" to "on a grant", in one function
`injectGoogleTags()` is split into `loadTags(granted)` and the existing mode resolution. The bootstrap computes the granted signals from the stored choice (`buildPayload`) and from every later `SCM_GCM.update()` call, and calls `loadTags` whenever the granted set grows:

| Granted signal | What may be requested |
| --- | --- |
| `analytics_storage` | direct mode: `gtag.js` with `config` for the GA4 id |
| `ad_storage` | direct mode: Ads `config` (and the Ads conversion), Meta Pixel (unchanged) |
| any of the four above, GTM mode | the GTM container |

`loadTags` is idempotent: it remembers what it already loaded in page memory, loads `gtag.js` at most once and only adds a `config` for a newly granted id. With nothing granted it does nothing, so there is no request, no cookie and no cookieless ping. The Consent Mode `default` stays at the top of the bootstrap; it is a dataLayer command, not a request. The runtime de-duplication against external containers stays as it is (checked when the module is about to load).

*Alternative considered:* keep loading the tag and use `gtag('set', 'url_passthrough')`/`ads_data_redaction` only. Rejected: that is advanced mode and still sends pings.
*Alternative considered:* load only after an explicit click and never for returning visitors until the next click. Rejected: a stored grant is a grant; returning visitors would be measured only after a second click.

### D2. Order after a grant: tag, update, then events
`SCM_GCM.update(store)` (called by the banner's `finalizeConsent`) does, in this order: (1) `loadTags` for the new grants, which for GTM pushes `gtm.js` and for direct mode appends `gtag.js` and the `config` commands, (2) `gtag('consent','update', payload)`, (3) the `scm_consent_update` event, (4) `flush()` of the page queue. Both `gtag.js` and `gtm.js` read the dataLayer asynchronously in order, so commands pushed in this order are processed in this order by the tag once it has loaded; the events therefore are not "lost" while the script is still downloading. Returning visitors take the same path at start-up: the bootstrap already pushes `default` and `update` in `<head>`; at `DOMContentLoaded` it calls `loadTags` and then `flush()`.

### D3. The queue stays in memory; the dataLayer sees nothing before a grant
Today `track()`/`event()`/`purchase()` queue until the tag mode is resolved and then push to the dataLayer, also in mode `none`. In basic mode the condition for leaving the queue changes from "mode resolved" to "a grant exists and its tag has been started". Until then entries stay in the array, are not pushed to the dataLayer (a later-loaded GTM would otherwise replay them with the wrong consent state), and die with the page. On an explicit reject (`update()` with no grant) the array is emptied. The queue is capped (the 100 newest entries) so a long page session without a choice cannot grow without bound. The fallback when the bootstrap is missing (`scm_ecommerce.js` pushing the dataLayer pair itself) stays: with no bootstrap there is also no tag loader, so nothing is requested.

### D4. Once-guards at delivery
`ecommerce_purchase.tpl` sets `scm_purchase_<id>` in `sessionStorage` before it calls `SCM_GCM.purchase()`. With a queue that is wrong: a visitor who reloads the confirmation page before choosing would find the guard set and never deliver the purchase after a grant. `track()`, `event()` and `purchase()` therefore accept an optional guard key as a third argument; the bootstrap checks and records it inside `dispatch*`, at delivery time. `scm_ecommerce.js` `once()` callers (`add_shipping_info`, user events) pass their key the same way and no longer write it themselves. Storage blocked: keep the current in-memory fallback.

### D5. Ads conversion needs `ad_storage`
`dispatchPurchase()` already sends the Ads `conversion` only when `mode.ads === 'gtag'`. `mode.ads` becomes `'gtag'` only after the advertising grant has loaded the Ads `config`; with analytics only, `mode.ads` stays `'none'`, so the GA4 `purchase` is delivered and the conversion is not. In GTM mode `mode.ads` stays `'container'`: the conversion belongs to the container.

### D6. GTM mode: what the module can and cannot promise
The module can promise that `gtm.js` is not requested without a grant. After an analytics-only grant the container is loaded and then runs whatever tags it holds. A Google Ads or remarketing tag inside the container with built-in consent checks would still fire a cookieless ping when `ad_storage` is denied (that is how Google's tags behave in advanced style inside a container). The "analytics-only loads no Ads tag" rule is therefore guaranteed by the module in direct mode only; in GTM mode it holds when the container's Ads and remarketing tags are set to require `ad_storage` (tag setting "Additional consent checks" in the container). The README gets a checklist, and the Integrations tab shows the notice required by the spec. The e2e test for GTM mode uses a stub container response and checks that the module itself makes no Ads request.

### D7. Banner: equal buttons and a footer link
- CSS: `.scm-btn-reject` and `.scm-btn-accept` get one shared rule (same neutral outlined style, same border width, no shadow, same font size and weight, `flex: 1 1 0` on desktop and full width at the same height on phones). `.scm-btn-save` is a third equal button but keeps its order after the two. "Akceptuję wszystkie" loses the brand fill and its shadow. The brand colour stays on focus rings and toggles. Brand colours remain configurable but cannot make one button heavier.
- Purchase button: the banner is a modal dialog with a backdrop while no choice exists (existing behaviour); after any choice it is hidden. The reopen button moves from bottom-left fixed overlay to a position that cannot sit over a sticky add-to-cart bar on phones: hidden below 600 px when the footer link is on (the footer link replaces it there), otherwise kept as is. Verified at 390 by 844 on a product page by a geometry test (no overlap of the add-to-cart button's rectangle).
- Footer link: `renderBannerAndEcommerce()` additionally returns a `<p class="scm-footer-link"><a href="#" class="scm-reopen-link">…</a></p>` using the existing `TXT_REOPEN` text, when a new config key `SHOW_FOOTER_LINK` (default 1, seeded by the upgrade) is on. Because the three hooks are all "end of page" candidates, a theme that prints none of them in the footer area still shows the link at the end of the body; the existing click handler already opens the banner.
  *Alternative considered:* ask each theme to print the link in its own footer. Rejected for the module (theme independence is a stated feature); the shop theme may still place a second link, both share the class `scm-reopen-link`.

**Owner decision 2026-11-16: two-screen bottom sheet after x-kom.pl.** The first screen is short (title, two or three sentences, privacy link, three buttons, no switches); the switches live on a second screen "Ustawienia ciasteczek" with one expandable card per category. "Akceptuję wszystkie" is the filled main action, "Ustawienia cookies" and "Odrzuć opcjonalne" are outlined. The 2023 EDPB cookie banner taskforce report treats colour emphasis case by case, so the first screen keeps a reject button of exactly the same size as accept, on the first screen, in view without scrolling. This replaces the earlier rule that no button carries the brand fill. Layout: under 768 px a full-width sheet docked to the bottom with stacked buttons (Akceptuję wszystkie, Ustawienia cookies, Odrzuć opcjonalne); from 768 px a card docked to the bottom centre, 848 px wide, with the buttons in one right-aligned row (Ustawienia cookies, Odrzuć opcjonalne, Akceptuję wszystkie) and no visible dimming. The DOM order of the first-screen buttons is switched by the script to match whichever layout the CSS applies, so Tab order equals the visual order. The settings screen (Wróć, Zapisz wybór, Akceptuję wszystkie) keeps the same order in both layouts and its button bar stays pinned while the cards and the legal text scroll. Optional switches never start on. Colours come from the existing primary and accent settings; the text colour on the filled button is computed for AA contrast. The tests use a navy brand: primary #004b87 and accent #146c43. The legal text and the data controller moved from the first screen to the settings screen; the 1.9.0 upgrade seeds the four new texts (settings button, Wróć, settings title and intro).

### D8. Retention
Admin validation changes to 1 to 365 (`scm_cookieconsent.php:608` and the matching message and the input `max` in `configure.tpl`). `upgrade-1.9.0.php` clamps a larger stored `SCM_COOKIE_EXPIRY_DAYS` to 365 and seeds `SCM_COOKIE_SHOW_FOOTER_LINK` = 1. The JS already honours the lifetime for the cookie and for the `localStorage` mirror (`readConsentStore`, line 93).

### D9. Tests: a request log, not just the dataLayer
The existing fixture aborts Google requests with `page.route`, which hides whether the page tried. A new fixture (`requests` in `helpers.js`) records every request URL (`page.on('request')`) before routing and fulfils analytics hosts with an empty `200` stub script (so the late-grant tests see a normal load). New spec `06-consent-basic.spec.js`:
1. no choice: open home, product, cart; log has no analytics/advertising host; no `_ga*`/`_gcl*` cookies;
2. reject, then three pages: same;
3. late grant on a product page: the log contains the tag request only after the click; the dataLayer order is consent `update`, `scm_consent_update`, then `view_item`; a full journey delivers all six events once in both modes (GTM stub and direct);
4. analytics only (direct mode, Ads id set): no Ads host in the log, GA4 `purchase` present, no `conversion`; add marketing later: `config` for Ads added, `gtag.js` requested once;
5. withdrawal: next page has no analytics request, `_ga` cookie gone;
6. reload of the confirmation page before choosing, then grant: `purchase` once; after delivery, reload: no second `purchase`;
7. button geometry at 390 by 844 and 1366 by 768 (computed style equality, add-to-cart not overlapped), footer link on five page types, retention of 365 days from the cookie expiry.
Existing specs call `go()`, which clicks "Akceptuję wszystkie" and then reads `SCM_GCM.mode` straight away; under basic mode the mode is resolved after the grant, so those reads move after the click completes (`waitFor` on `SCM_GCM.ready`). The suite's stack and port stay as documented in `tests/e2e/README.md`.

### D10. Release
Version 1.9.0 (new behaviour, a config key, a stricter admin limit). `$this->version` in `scm_cookieconsent.php:40`, `upgrade/upgrade-1.9.0.php`, `README.md` ("Google tag modes", "Consent Mode v2", hooks, the new key, the container checklist, a "Measurement effect" note), `installConfig()`/`uninstallConfig()`/`getAllConfig()` entries for the new key, `build.ps1` produces the zip, the minified `scm_cookieconsent.min.js` and the bootstrap copy in the `.tpl` are regenerated and checked against their sources.

## Reconciliation with the in-flight changes

Both changes are nearly done (`complete-ga4-ecommerce-measurement` 29/30, `add-google-ads-conversion-tracking` 17/18; the open items are manual staging checks). Their code is already in 1.8.0, and their specs are still deltas, so `openspec/specs/` is empty.

**Order.** Recommendation: land this change after both are archived. The two remaining manual checks (6.4 and 5.3) should be run against 1.8.0 first, because that gives the owner the last advanced-mode measurement baseline; note that 5.3(e) is superseded by this change and need not pass in its old form. Once they are archived their requirements exist in `openspec/specs/`, and the two new capabilities here can be rewritten as `MODIFIED` deltas where noted below. If this change must land first (the owner wants the consent fix live before the staging checks), nothing in the code depends on the order: this change only edits the places the others created, and the archive of the others would then need the superseded requirements below adjusted.

**`add-google-ads-conversion-tracking`**
- `google-ads-conversion-tracking` / "Consent handling for conversions" says the conversion "SHALL be submitted regardless of the visitor's marketing consent state". **Conflicts.** Superseded by "Ads conversion only after advertising consent" here. Its scenario "Marketing consent denied" (conversion still sent) becomes "no conversion", and manual check 5.3(e) ("hit still sent with `gcs` showing ads denied") is no longer expected. The "Consent Mode disabled" scenario stays true.
- `google-tag-integration` / "Google tags load only when Consent Mode is enabled" stays true; this change adds a second condition (a grant). Its scenario "Consent default precedes the tag" stays true and is strengthened (the default also precedes any request because requests now come later).
- `google-tag-integration` / "Tag mode resolution": the mode is no longer resolved at `DOMContentLoaded` on every page; it is resolved when the first grant starts a tag. Without a grant both targets are `none` (this matches the existing "No Google tag" scenario). Scenarios "Own direct gtag.js" and "Container present…" hold after a grant.
- `google-tag-integration` / "Pre-resolution event queue": events are no longer dispatched "immediately after resolution"; they are dispatched after a grant, and dropped without one (D3). Order preservation is unchanged. Convert to `MODIFIED`.
- "Per-order de-duplication" (the purchase guard) changes timing (D4); the observable rule (once per order) is unchanged.
- "Ads-only direct tag alongside a container" (`ADS_FORCE_DIRECT`): loads only after the advertising grant.

**`complete-ga4-ecommerce-measurement`**
- Its spec says events are delivered "through the single entry point" and are sent whatever the consent state because Consent Mode governs the tag (`scm_ecommerce.js` header comment: "pushes are made unconditionally"). Under basic mode a push is a queue entry until a grant; event names, payloads and once-rules are untouched. The new header comment in `scm_ecommerce.js` must say so.
- `ga4-user-events` / "Pending events survive redirects": the pending login/sign-up marker is consumed by the next page whether or not the visitor has consented, so a login by a visitor without a grant is not reported. That is the intended basic-mode outcome. Noted, no change.
- Its manual check 6.4 (GA4 DebugView and GTM Preview journey) needs a granted visitor; run it after granting analytics.
- The six events in this change's brief are all in its list; `view_item_list`, `select_item`, `view_cart`, `remove_from_cart`, `login`, `sign_up` and `search` use the same queue and get the same behaviour for free.

## Risks / Trade-offs

- [GA4 and Ads figures fall, no modelled data for refusers] -> accepted by the owner; the README says so, and the shop's own order tables stay the reference.
- [Direct mode now loads `gtag.js` later (after a click or at DOMContentLoaded on return)] -> a few early events are queued rather than lost; events raised before the visitor's first choice on the first page are delivered only if they choose to accept.
- [A GTM container's own Ads tags can ping with `ad_storage` denied] -> D6 checklist and notice; cannot be enforced by the module.
- [An external module (TagConcierge, PS Marketing with Google) keeps loading its own container] -> notice in the Integrations tab; the existing runtime de-duplication means this module does not add a second one. Document how to disable that module's loading or configure it to wait for the `scm_consent_update` event.
- [Minified bootstrap copy drifts from the source] -> add a build-time check in `build.ps1`/CI that re-minifies the source and compares it with the `.tpl` payload (the previous change left this as a follow-up; this change touches that file heavily).
- [Visitors who ignore the banner entirely produce no data] -> inherent to basic mode.
- [Equal buttons may lower the accept rate] -> inherent to the requirement; measured by the shop's own tables, not GA4.

## Migration Plan

1. Run the manual checks 6.4 and 5.3 of the in-flight changes on 1.8.0, archive them (`openspec archive`), then convert the two deltas here to `MODIFIED` where the table above says so (`openspec validate --strict`).
2. Implement and test per `tasks.md` on a branch; build the zip with `build.ps1`; install over 1.8.0 on a staging shop; check the upgrade script (lifetime clamp, new key).
3. Release as 1.9.0. Rollback: reinstall the 1.8.0 zip; the new config key is ignored by 1.8.0 and the clamped lifetime stays valid, so no data migration is needed in either direction.
